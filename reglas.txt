================================================================================
INTESIS — REGLAS PARA ASISTENTES DE IA (Claude, Codex, Copilot, Cursor, etc.)
================================================================================
Última actualización: 2026-06-15
Usar este archivo como guía obligatoria antes de generar o modificar cualquier
código. Estas reglas reflejan las decisiones técnicas ya tomadas en el proyecto.
================================================================================


── PHP ─────────────────────────────────────────────────────────────────────────

1.  declare(strict_types=1) en TODOS los archivos PHP sin excepción.
2.  Namespace base: Intesis\  (ej: Intesis\Controladores\, Intesis\Modelos\)
3.  Los controladores son clases final que usan el trait ControladorComun.
4.  Los modelos son clases final. Acceden a PDO via $this->conexionBaseDatos->obtener()
    o un helper privado pdo(): \PDO.
5.  NO usar Eloquent, Doctrine ni ningún ORM. Solo PDO con prepare/execute.
6.  NO usar autoloader de Composer para clases propias; se cargan con require_once
    en index.php en el orden: Nucleo → Modelos → Controladores.
7.  Toda escritura en BD va dentro de transacción: beginTransaction / commit /
    rollBack en el bloque try/catch del modelo.
8.  Validaciones de negocio se lanzan con throw new \InvalidArgumentException().
    Errores de BD o lógica inesperada con throw new \RuntimeException().
9.  Los controladores capturan Throwable y llaman a responderJson() o redirigir().
10. NUNCA poner lógica SQL en controladores. Todo SQL va en modelos.
11. Las migraciones son archivos .sql en /migrations/, con nombre
    YYYYMMDD_HHMM_descripcion.sql. Deben ser idempotentes (IF NOT EXISTS /
    WHERE NOT EXISTS). Nunca modificar una migración ya ejecutada; crear una nueva.
12. AVISAR explícitamente cuando haya SQL pendiente de ejecutar en la BD.


── BASE DE DATOS (PostgreSQL) ───────────────────────────────────────────────────

13. Motor: PostgreSQL 17. Driver: PDO con DSN pgsql.
14. Prefijos de columna = prefijo de la tabla.
    Ejemplo: tabla ven_cliente → columnas ven_cliente_id, ven_cliente_nombre, etc.
    NUNCA añadir sufijos de origen (_sri, _interno, _prov) sin confirmación.
15. Estados de entidades se gestionan via tabla sis_estado:
    (sis_estado_modulo, sis_estado_entidad, sis_estado_codigo, sis_estado_nombre).
    No usar columnas booleanas de estado cuando ya existe sis_estado_id.
16. Secuencias de documentos: tabla sis_secuencias vinculada a sis_tipo_documento.
    Usar SecuenciaModelo::obtenerSiguiente($pdo, $empresaId, $tipoCodigo, $modulo).
17. Tipos de documento registrados en sis_tipo_documento con código y módulo.
    Módulo VENTAS: FACTURA_VENTA, NOTA_VENTA, PROFORMA, NOTA_CREDITO, etc.
18. El campo sis_empresa_id está en TODAS las tablas de negocio (multi-empresa).
19. Auditoría mínima obligatoria: usuario_crea, fecha_crea en INSERT;
    usuario_modifica, fecha_modifica en UPDATE.
20. Nunca DELETE físico en tablas de negocio. Usar estado ELIMINADO o campo _estado=0.
21. IDs de estado: nunca hardcodear el número; siempre buscar por código con SELECT.


── ARQUITECTURA MVC ─────────────────────────────────────────────────────────────

22. Flujo de una petición:
    index.php → Aplicacion::iniciar() → Enrutador::despachar()
              → Controlador::metodo() → Modelo → Vista

23. Para agregar un módulo nuevo se deben tocar EXACTAMENTE estos 4 archivos:
    a) index.php         — require_once del Modelo y del Controlador
    b) Aplicacion.php    — use, instancia del modelo, instancia del controlador,
                           pasar al constructor de Enrutador
    c) Enrutador.php     — use, propiedad privada, rutas GET/POST
    d) Vista(s)          — archivos en src/Vistas/<modulo>/

24. Las rutas siguen el patrón /<modulo>/<entidad>/<accion>.
    Vistas GET:             /ventas/facturas, /ventas/facturas/nuevo, /ventas/facturas/editar
    Acciones POST (JSON):   /ventas/facturas/guardar, /ventas/facturas/anular
    Endpoints apoyo (JSON): /ventas/facturas/detalle, /ventas/facturas/buscar-cliente

25. responderJson(bool $ok, string $codigo, string $mensaje, array $data = [])
    es el único mecanismo para respuestas JSON. Termina con exit internamente.

26. Las vistas reciben variables por array asociativo desde el controlador.
    NO usar variables globales en vistas.


── FRONTEND ─────────────────────────────────────────────────────────────────────

27. CSS framework: Bootstrap 5 + AdminLTE 4. Clases personalizadas: btn-intesis,
    btn-secundario, tabla-intesis, modal-intesis, breadcrumb-navbar, etc.
28. Tablas con DataTables: SOLO las que tienen clase tabla-intesis se inicializan
    automáticamente (sistema.js línea 95). Las tablas dentro de modales NO deben
    tener esa clase o se romperá el layout.
29. Alertas y confirmaciones: SweetAlert2 (Swal). Color corporativo: #1f6f68.
30. Iconos: Bootstrap Icons (bi bi-*).
31. Las peticiones AJAX desde las vistas usan fetch() nativo con JSON.
    Respuesta esperada: { ok: bool, codigo: string, mensaje: string, data: {} }
32. Los botones de navegación (Nuevo, Cancelar) deben ser <button type="button">
    con onclick="window.location.href=..." en lugar de etiqueta <a>.
33. Los formularios de creación/edición no usan <form> con submit; el guardado
    se hace via fetch() POST con Content-Type: application/json.
34. El JS de las vistas es vanilla (sin jQuery) envuelto en IIFE (function(){})().
    Se declara 'use strict'; al inicio del bloque.
35. Helper const q = (sel) => document.querySelector(sel) se usa en todas las vistas.


── PERMISOS Y SEGURIDAD ────────────────────────────────────────────────────────

36. Cada acción del controlador llama primero a exigirSesion() o exigirSesionJson().
37. Luego llama a exigirPermiso('/ruta/accion') o exigirPermisoJson().
38. Los permisos se registran en sis_menu (tipo 'B' = botón/acción) y se asignan
    en sis_perfil_permisos. El superusuario tiene todos los permisos.
39. Cada módulo nuevo debe insertar en la migración:
    - Menú padre (tipo 'M') con su URL
    - Acciones (tipo 'B'): ver, crear, editar, anular (según aplique)
    - Permisos para el perfil superusuario vía sis_perfil_permisos


── CONVENCIONES DE NOMBRADO ────────────────────────────────────────────────────

40. Clases PHP:     PascalCase con sufijo del tipo (FacturaModelo, FacturaControlador).
41. Métodos:        camelCase (listar, buscar, crear, actualizar, anular).
42. Variables PHP:  camelCase ($empresaId, $formaPagoId).
43. Columnas BD:    snake_case con prefijo de tabla (ven_documento_fecha_emision).
44. Códigos:        MAYUSCULAS_CON_GUION_BAJO (CREADA, FACTURA_VENTA, VEN_DOCUMENTO).
45. Archivos vista: snake_case (factura_form.php, proforma_form.php).
